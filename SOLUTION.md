# Решение

Коротко: скидки добавил, причина жалобы — переход Берлина на летнее время, а `result.json` совпадает
с ответом, который я посчитал отдельно от сервиса. По дороге исправил ещё четыре проблемы, влиявшие на те же
суммы или на надёжность: потерю копейки, гонку вебхуков, 500 вместо 4xx и медленный синк.

## Что сделано

**Скидки.** `daily-totals` отдаёт по каждому дню `{ date, total, gross, discount, net }`: `gross` — сумма `amount`
оплаченных заказов, `net` — сумма `amountPaid`, `discount = gross − net`, `total` по-прежнему равен `gross`.
Считаю в целых копейках, в рубли перевожу только в ответе. У заказов в старом формате, без полей скидки,
оплаченной считается вся сумма. `discountPercent` не читаю: для ответа он не нужен.

Миграция `002_amount_paid.sql` добавляет колонку `amount_paid_kop`. У заказов, которые уже лежат в базе работающего
сервиса, оплаченная сумма неизвестна, а среди них есть и заказы со скидкой. Если записать им «оплачено полностью»,
ошибка останется навсегда: версия заказа в API не изменилась, и синк пропустит его как устаревший. Поэтому колонка
у них остаётся пустой (`NULL`): до ближайшего синка такие заказы считаются оплаченными полностью, как раньше,
а синк загружает сумму даже из той же версии заказа — но не из более старой.

**Жалоба по `c_7`.** Смещение таймзоны теперь берётся на момент каждого заказа, а не на «сейчас»
(`dateInTimeZone` в `utils/time.ts`). Подробности — в следующем разделе.

**Ещё четыре исправления:**

- **Копейка.** `toKop` делал `Math.floor(rub * 100)`, а `1147.62 * 100 = 114761.99999999999` — копейка терялась.
  На `amount` этого не видно, там целые рубли, а на `amountPaid` видно: `net` в 4 днях из 5 выходил меньше
  на 1–2 копейки. Теперь значение, которое отличается от целого не больше чем на погрешность float, считается
  целыми копейками, а настоящие доли копейки по-прежнему отбрасываются.
- **Гонка вебхуков.** `apply()` читал заказ, сравнивал `updatedAt` и записывал — тремя шагами. Внешняя система
  присылает старую и новую версию одновременно, и старая могла перезаписать новую. Теперь сравнение и запись —
  один запрос: `INSERT … ON CONFLICT (id) DO UPDATE … WHERE orders.updated_at < excluded.updated_at`.
- **500 вместо 4xx.** Обработчик ошибок превращал в 500 всё, кроме `AppError`, включая битый JSON и чужой
  `Content-Type`. Заметил, когда `POST /sync` из PowerShell (`Invoke-RestMethod`) вернул 500. Отправитель вебхуков
  повторяет ответы 5xx, то есть повторял бы заведомо плохой запрос. Теперь такие ошибки отдаются со своим кодом
  (`bad_request`, `unsupported_media_type`), а 500 остаётся для внутренних сбоев.
- **Медленный синк.** Каждый заказ сохранялся отдельным запросом (вместе с чтением — двумя), а запрос к Postgres
  в Docker Desktop под Windows стоит около 44 мс: синк 5030 заказов шёл 7,5 минуты. Теперь страница из 100 заказов
  сохраняется одним запросом с той же проверкой «только если новее», и вебхук идёт через тот же запрос. Синк
  занимает 16 секунд — почти всё это ожидание лимита API. Один запрос не может обновить строку дважды, поэтому
  повторы заказа на странице сводятся к самой свежей версии, остальные считаются `stale` (у реального API
  повторов на странице нет).

И мелочь: раз смещение таймзоны теперь нужно для каждого заказа, `Intl.DateTimeFormat` кешируется по таймзоне —
так в 10 раз быстрее.

**Тесты.** Их 41, все зелёные. Добавил тесты на скидки, переход на летнее время, копейку, гонку, коды ошибок,
синк и обновление базы. Гонку тест воспроизводит детерминированно: прямо перед записью старой версии подсовывает
«параллельную доставку» новой. Обновление — тоже честно: откатывает миграцию 002 на тестовой базе, сохраняет заказ
так, как это делала прежняя версия, и применяет миграцию заново. Тесты на гонку, на «страницу одним запросом»,
на обновление базы и на долю копейки я прогнал на копии проекта с кодом до исправления — там они падают. В трёх
старых тестах `totals.test.ts` ответ сравнивается целиком, поэтому в их ожидания пришлось дописать новые поля;
значения `total` не менялись. `createContainer(db, api)` и `OrdersApi` не трогал.

## Причина расхождения и как нашёл

У `c_7` таймзона `Europe/Berlin`, а 29 марта Берлин перешёл с UTC+1 на UTC+2. Сервис вычислял смещение один раз,
на текущий момент, и применял его ко всем заказам. Сейчас ноябрь, смещение +1, поэтому заказ от 29 марта
22:40 UTC — в Берлине это уже 00:40 30 марта — попадал в 29-е. Сходились только дни до перевода часов, 27 и 28.
Летом ошибались бы другие дни: ответ зависел от того, когда его запрашивают.

Как нашёл:

1. Жалоба сама подсказывала: конец марта, часть дней, таймзона клиента. В `totals.ts` смещение бралось на `new Date()`.
2. Воспроизвёл на исходном коде по процедуре из `TASK.md`: `total` за 27–31.03 — 24736, 58233, **43964**,
   **52201**, **44064**.
3. Посчитал то же в SQL, где день определяется для каждого заказа отдельно:
   `(created_at AT TIME ZONE 'Europe/Berlin')::date`. Получилось 24736, 58233, **34658**, **59684**, **35401**.
4. Разница — ровно 4 оплаченных заказа около полуночи после перевода часов: `o_02357`, `o_02448`, `o_02545`
   и `o_02547`.

## Что ещё заметил

Внешний API (всё проверено запросами к нему):

- `nextCursor` не бывает `null`, хотя README это обещает: в конце приходит пустая страница с тем же курсором.
  `limit` по умолчанию — 50.
- Лимит — 5 запросов за любые 1000 мс, общий для всех путей, даже для 404; у каждого третьего ответа 429 нет
  `Retry-After`. Иногда вместо 429 приходит `200 {"error":"rate_limited"}` без `items`. Если принять такой ответ
  за конец данных, синк потеряет всё после этой страницы, включая 50 «поздних» заказов в хвосте списка.
- Формат плавает: `amount` и `discountPercent` иногда приходят строками, `createdAt` — без зоны (это UTC). Поля
  скидки есть только у заказов с 15.03 и всегда приходят парой.
- Вебхуки приходят по 2–3 раза, не по порядку и пачками одновременно; бывает, что старая версия приходит после
  новой. Отправитель повторяет только 5xx и сетевые ошибки, а ответ 400 считает окончательным — слишком строгая
  валидация молча теряет обновления. На 5xx отправитель делает до 30 попыток на каждую копию (около 15 секунд),
  потом обновление теряется. Если сервис не отвечает вовсе 15 секунд, отправитель останавливается целиком.

Код и окружение:

- `.env` никто не читает: работают дефолты из `config.ts`, которые совпадают с `.env.example`.
- Чтобы получить чистую базу, нужен `docker compose down -v`: `up -d` при существующих контейнерах её не очищает.
- Сервис падает при старте, если PostgreSQL ещё не принимает соединения: в свежем контейнере это первые секунды
  после `docker compose up -d`, а повторных попыток нет.
- Вебхуки ничем не подписаны, у `daily-totals` нет ограничения на длину периода, миграции не защищены
  от одновременного запуска, а `import.meta.dirname` в `db.ts` требует Node 20.11+, хотя в `engines` — `>=20`.
- На ноябрь 2026 года `npm audit` находит 7 известных уязвимостей, в рабочих зависимостях две — fastify 5.2.1
  и zod 3.24.1. По описаниям они касаются того, чем сервис не пользуется, но обновить стоит отдельной задачей.

## Допущения

- День заказа — по `createdAt` в таймзоне клиента, как и раньше, а не по моменту оплаты.
- Статистика показывает текущее состояние: заказ, возвращённый позже, пропадает из своего дня задним числом.
- `net` — сумма `amountPaid`; если поля нет, заказ оплачен полностью. `discount` считаю как `gross − net`,
  а не из процента.
- После обновления сервиса нужен `POST /sync`, чтобы загрузить оплаченные суммы у ранее сохранённых заказов;
  до него они считаются оплаченными полностью.
- Из версий одного заказа побеждает версия с бóльшим `updatedAt`, при равном — первая (так было и раньше).
- Суммы в ответе — числа в рублях с копейками (`2087.5`), как в примере из задания.

## Как проверял

- `npm test` — 41 тест на реальной базе, `npm run typecheck` — без ошибок.
- Посчитал правильный ответ отдельным скриптом, без кода сервиса: забрал все заказы из `/orders` и все вебхуки
  через временный приёмник, взял самую свежую версию каждого заказа и сложил суммы по берлинским дням.
  `result.json` совпал с ним до символа.
- Всю процедуру из `TASK.md` прогнал с чистой базы восемь раз на разных этапах — ответ каждый раз тот же. Один
  прогон — из свежего клона репозитория с GitHub по README, последний — дословно командами из раздела ниже. Ещё
  один — с сервисом в таймзоне Нью-Йорка, а тесты — в таймзонах Лос-Анджелеса и Киритимати (UTC+14): от таймзоны
  машины результат не зависит.
- Обновление с исходной версии на данных мока: исходный код забрал все 5030 заказов, затем новая версия применила
  миграцию 002 к заполненной базе, синк загрузил оплаченные суммы (скидка нашлась у тех же 1806 заказов, что и
  на чистой базе), дальше вебхуки — ответ совпал с `result.json`. До исправления после такого обновления скидка
  была только у 18 заказов, которых коснулись вебхуки.
- Перебором: перевод в копейки — на всех суммах до 1 000 000 ₽, причём доли копейки отбрасываются, даже если
  до целой осталось 10⁻⁸; даты — на 1,13 млн моментов в 16 таймзонах, включая переходы на летнее время и сдвиги
  на 30 и 45 минут.
- Поведение API и отправителя вебхуков — опытами: тип лимита, повторы на 503 и их отсутствие на 400, остановку
  через 15 секунд без ответа; на живом сервисе — битый JSON → 400 и чужой `Content-Type` → 415.

Как получить `result.json`:

```bash
docker compose down -v && docker compose up -d
until docker compose exec -T postgres pg_isready -h 127.0.0.1 -U postgres -q; do sleep 1; done
npm start   # в отдельном терминале; миграции применяются при старте, дождаться «Server listening»
curl -X POST http://localhost:3000/sync
docker compose run --rm orders-api webhooks --target http://host.docker.internal:3000/webhooks/order
curl -o result.json "http://localhost:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31"
```

## Что бы доделал

- Подпись вебхуков и ограничение длины периода в `daily-totals`.
- Обновление таймзоны клиента: сейчас она кешируется навсегда.
- Контрактные тесты клиента внешнего API на записанных ответах: фейковый лимит, 429 без `Retry-After`,
  пустая последняя страница.
- Блокировку вокруг миграций, повтор подключения к базе при старте и обновление зависимостей.
